# 의미 기반 매칭·등록 추천 로드맵

문서 표준화(`POST /api/transform`, `/governance/transform`)를 문자열·패턴 일치에서 **의미가 맞는 엔티티만 대상으로 하는 구조**로 확장하고, 등록되지 않았지만 의미가 비슷한 용어를 **등록 추천**하기 위한 후속 작업 목록이다.

## 현재 상태 (2026-10-07 기준)

- 문서 표준화는 RDB의 활성 Term·Expression·Rule만 사용한다. vectorDB·임베딩은 쓰지 않는다.
  - 용어 치환: 등록된 Expression과 문자열 일치(정규화·단어 경계·조사 보정) → Term 이름으로 치환
  - MASKING: 매칭 패턴 → 치환 형식 → 수정 완료 패턴 검증
  - PROHIBITED(`notContains`): 남은 위반 보고만
  - FORMAT / ENUM / RANGE / REQUIRED / RELATION / CUSTOM: 값과 Term의 연결이 없어 미적용(`skipped`)
- 업로드 문서는 저장하지 않는다.
- 인증·권한이 없다.
- 기본 임베딩은 `mock`이라 유사도 점수에 의미가 없다.
- 관련 코드: `src/domain/transform.ts`, `src/application/transform.ts`, `src/app/api/transform/route.ts`, `src/components/document-transform.tsx`
- 샘플: `docs/samples/customer-onboarding.md`

## 해결하려는 문제

| 문제                 | 예시                                                 | 현재 동작                 |
| -------------------- | ---------------------------------------------------- | ------------------------- |
| 같은 글자, 다른 의미 | "고객의 **나이**" vs "**나이**가 들수록 이용이 준다" | 둘 다 고객연령으로 치환   |
| 같은 패턴, 다른 값   | 13자리 숫자가 주민등록번호인지 주문번호인지          | 패턴이 맞으면 모두 마스킹 |
| 다른 글자, 같은 의미 | "개인 식별 번호" ≈ 주민등록번호                      | 미등록이라 찾지 못함      |
| 미등록 개념          | "여권번호"처럼 거버넌스에 없는 데이터 개념           | 아무 보고 없음            |

| 단계 | 작업                                 | 선행 조건 | 목적                             |

| 6    | 피드백 반영·검토 UI 고도화·감사 기록 | 3, 4, 5   | 운영 품질 유지                   |

## 0. 의사결정 (착수 전)

- [ ] **문맥 판정·초안 작성 모델**: 외부 LLM(Claude 등) / 사내·로컬 모델 / LLM 미사용
  - 외부 LLM이면 개인정보 전송 설계(5단계의 자리표시자 방식)가 필수다.
- [ ] **임베딩 모델**: Qwen3-Embedding 등 실제 모델 확정, 한국어 짧은 구절 품질 확인
- [ ] **추천 수락 시 상태**: 바로 `ACTIVE` / `DRAFT` 등록 후 승인
- [ ] **근거 문맥 저장 정책**: 마스킹 후 저장 / 구절·통계만 저장
- [ ] **적용 방식**: 고신뢰 자동 적용 + 중간 신뢰 제안 / 모든 변경 사람 검토
- [ ] **승인자 역할**: 누가 Term·Expression 등록을 승인하는가

## 1. Markdown AST 파싱과 값-엔티티 연결

정규식 구간 분리(`splitProtected`)를 구조 파싱으로 바꾸고, 값이 어떤 엔티티에 속하는지 연결한다. LLM 없이도 오탐이 크게 줄고, 미적용 규칙 유형까지 적용할 수 있게 된다.

- [ ] remark(mdast) 등으로 표·목록·문단·코드·링크를 노드 단위로 구분
- [ ] 위치 정보(offset)를 유지해 원문 서식을 보존한 채 치환
- [ ] 값-엔티티 연결
  - 표: 열 헤더 → Term, 해당 열의 셀 값 → 그 Term의 값
  - `키: 값`, 목록의 `- 키: 값`
  - 문장 내 수식어("주민등록번호 900101-…")
- [ ] 연결된 값에만 해당 Term의 규칙 적용
  - MASKING: 주민등록번호 열·라벨에 연결된 값만 마스킹 (연결 없는 패턴 일치는 "확인 필요"로 보고)
  - FORMAT / ENUM / RANGE / REQUIRED: 연결된 값으로 판정해 위반 보고
- [ ] 결과 보고에 변경별 근거(어느 헤더·라벨로 연결됐는지) 추가
- [ ] 표 치환 후 열 정렬 공백 재계산(선택)
- [ ] 테스트: 기존 `tests/transform.test.ts` 유지 + 표·키값·문장 연결 사례 추가

## 2. 평가셋 구축

의미 기반 판정은 바꿀 때마다 결과가 달라지므로 정답 데이터가 먼저 있어야 한다.

- [ ] 문맥 판정용: 정답 표시된 샘플 문서 묶음 (언급 위치, 정답 Term 또는 "해당 없음")
  - `docs/samples/customer-onboarding.md`를 시작점으로 확장
  - 같은 글자·다른 의미, 같은 패턴·다른 값 사례를 의도적으로 포함
- [ ] 동의어 판정용: (구절, Term, 동의어 여부) 쌍
- [ ] 평가 스크립트: Term별 precision / recall, 추천 정확도
- [ ] CI 또는 수동 회귀 기준치 기록

## 3. 실제 임베딩 연결과 등록 추천 (1차)

이 단계부터 vectorDB와 실제 임베딩 모델이 필수다.

### 3-1. 후보 구절 추출

- [ ] 구조적 위치 우선: 표 헤더, `키: 값`의 키, 굵은 글씨
- [ ] 본문 명사구: 한국어 형태소 분석기(Kiwi 등) 또는 LLM 추출
- [ ] 필터: 이미 등록된 표현(정규화 일치), 불용어·일반어, 최소 출현 빈도

### 3-2. 유사도 비교와 추천 분류

- [ ] 구절을 문맥과 함께 `embedQuery` → Term·Expression 인덱스 검색
- [ ] 점수 구간으로 분류 (임계값은 2단계 평가셋으로 조정)

| 구간 | 분류            | 예시                                   |
| ---- | --------------- | -------------------------------------- |
| 높음 | Expression 추천 | "개인 식별 번호" → 주민등록번호의 표현 |
| 중간 | LLM 검증 대상   | (5단계 전에는 낮은 신뢰로 표시)        |
| 낮음 | Term 추천 후보  | "여권번호" → 새 Term                   |
| 복수 | 모호성 알림     | "회원 ID" ≈ 고객번호, 계약번호         |

- [ ] 짧은 구절 ↔ 긴 정의의 비대칭 문제 확인. 필요하면 인덱싱 텍스트 형식 조정(`textFormat` revision 증가 → 전체 재인덱싱)

### 3-3. 추천 저장소 (신규 테이블)

- [ ] `recommendations` 테이블
  - 구절, 정규화 구절, 유형(EXPRESSION / TERM / AMBIGUOUS), 추천 Term, 점수
  - 근거 문맥(0단계 정책에 따라 마스킹 후 저장 또는 미저장)
  - 출현 횟수, 문서 수, 최초·최근 발견 시각
  - 상태(PENDING / ACCEPTED / REJECTED / MERGED), 결정자, 결정 시각, 거절 사유
  - 임베딩 프로필·모델 버전
- [ ] 정규화 구절 기준 중복 합치기 (문서 간 누적)
- [ ] 거절된 추천은 재추천하지 않음
- [ ] migration 추가, 기존 migration 수정 금지(checksum 검증)

### 3-4. 기본 검토 화면과 표준화 연결

- [ ] 추천 목록 화면: 출현 빈도순, 유형·상태 필터
- [ ] 수락 → 기존 `GovernanceService.create`로 Expression / Term 생성 (인덱싱은 기존 큐가 처리)
- [ ] Term 추천 수락 시 Term 폼을 초안으로 채워 열기
- [ ] 문서 표준화 결과에 "등록 추천" 섹션 추가. 추천 구절은 자동 치환하지 않음

### 3-5. 구조

- [ ] 추천은 별도 서비스로 분리(검색 포트 의존). vectorDB 장애 시에도 기본 표준화(RDB 전용)는 동작해야 한다.
- [ ] `createRuntime`의 임베딩·LanceDB 결합 정리 (RDB 전용 모드 설정 검토)

## 4. 인증과 승인 권한

현재 인증이 없어 누가 표준을 바꿨는지 알 수 없다. 추천 수락은 표준 데이터를 바꾸는 행위이므로 선행되어야 한다.

- [ ] 로그인(사내 SSO 등) 연동
- [ ] 역할: 조회자 / 작성자 / 승인자
- [ ] 추천 수락·Term 등록·Rule 변경을 승인자로 제한
- [ ] 변경 이력에 사용자 기록
- [ ] API 전반 권한 검사, 상태 변경 요청 CSRF 보호, 업로드·추천 API rate limit

## 5. LLM 문맥 판정과 추천 검증

- [ ] 문맥 판정: 후보 언급 + 주변 문맥 + 후보 Term의 정의·도메인 → "이 언급이 이 엔티티인가" + 신뢰도 + 근거
- [ ] 신뢰도 정책: 높음 자동 적용 / 중간 제안 / 낮음 무시 (0단계 결정에 따름)
- [ ] 추천 검증: "이 구절이 이 Term의 동의어인가" 판정으로 오추천 감소
- [ ] Term 추천 초안: 정의·도메인·필요 규칙(마스킹 대상 여부 등) 초안 생성
- [ ] **개인정보 처리**: 패턴에 걸린 값은 `[[VAL_1]]` 같은 자리표시자로 바꿔 전송. LLM은 판정만 하고 실제 마스킹은 서버 코드가 수행
- [ ] **프롬프트 인젝션 방어**: 문서는 데이터로만 전달, 지시와 분리. BLOCK 판정을 LLM 출력에만 의존하지 않음
- [ ] 구조화 출력(JSON schema / tool use)으로 응답 형식 고정
- [ ] 평가셋으로 규칙 기반(1단계) 대비 개선 확인 후 활성화

## 6. 피드백·운영

- [ ] 거절 결과를 문맥 판정의 부정 예시로 저장 ("이 문맥에서는 이 Term 아님")
- [ ] 데이터 모델 보강
  - Expression 매칭 정책: `EXACT`(바로 적용, 예: RRN) / `CONTEXTUAL`(문맥 판정 필요, 예: 나이)
  - Term 부정 예시
  - 문서 유형을 받아 Rule `scope`(예: `document: EXTERNAL`) 실제 판정
- [ ] 검토 UI 고도화: 변경별 수락·거절, 근거·신뢰도 표시, 일괄 처리
- [ ] 감사 기록: 변경 근거, 모델·임베딩 버전, 결정자 (원문은 저장하지 않음)
- [ ] 지표: 추천 수락률, 자동 적용 후 되돌림 비율, Term별 precision 추이

## 알려진 제약 (현재 구현)

- 짧은 일반어("나이")를 Expression으로 등록하면 의도치 않은 곳까지 치환될 수 있다 → 6단계 매칭 정책으로 해결
- 조사 보정은 조사가 단독으로 붙은 경우만 처리한다("나이이다" 등은 그대로)
- 마스킹 규칙 정규식을 최대 1MB 문서에 그대로 실행한다. 관리자만 규칙을 등록한다고 가정하며, 정규식 실행 시간 제한은 없다
- seed의 PROHIBITED 패턴이 MASKING 매칭 패턴과 같아 위반이 보고되는 경우가 없다
